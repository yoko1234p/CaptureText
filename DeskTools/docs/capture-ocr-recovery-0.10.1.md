# CaptureText 0.10.1 OCR recovery

On 2026-10-29 a long-running CaptureText process produced repeated macOS TextRecognition E5RT code 13 logs while the user reported recognition failures. A new process read the synthetic Traditional Chinese fixture successfully. These observations do not establish why the system runtime failed, or prove that every E5RT error is recoverable.

When a Vision text request throws, the app now checks cancellation and retries once using a fresh request configured with the advertised CPU device for every stage. If the retry fails or CPU is unavailable, the original error remains visible. Automatic-language supplemental rectangle detection is best-effort; failure does not discard text already recognised. No new engine, downloaded model, or network access is involved.

Validation was scoped to CaptureText: 73 capture tests passed, including injected Vision failure with actual CPU inference and cancellation before retry. The signed 0.10.1 app recognised an imported synthetic image and a simulated screen selection using the capture URL and an owned fixture. The original status-menu selection automation could not open its hidden menu and did not reach OCR. On a cold launch the first image check exceeded the previous nine-second test timeout; after extending that test's wait it passed. The existing result text was held in memory and restored after testing. Test preferences were restored and the system clipboard was not modified. This does not prove physical mouse operation, recovery from the original exact E5RT failure, extended sleep/wake behaviour, or every language and image.
